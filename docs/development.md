# Development

The local loop: set up, build, run, regenerate. Shipping a build is [release.md](release.md).

## Requirements

- Xcode 26. The app targets macOS 14 and later (`deploymentTarget` in `project.yml`).
- [XcodeGen](https://github.com/yonaskolb/XcodeGen): `brew install xcodegen`.
- The network, once, for the first build: SwiftPM fetches Hummingbird and the packages it depends on.

## First-time setup

Create the `Zubi Self-Signed` code-signing identity once. Every local build signs with it, and that is
what keeps macOS from forgetting the Reminders, Calendar and Automation (Notes) grants on every
rebuild. Follow **[signing.md](signing.md) §1**, a few `openssl`/`security` commands.

That is the whole required setup.

## The project

`Zubi.xcodeproj` is generated by XcodeGen from `project.yml`, and the generated project is
**committed**, `Package.resolved` included, because the release workflow builds it as-is. After editing
`project.yml`, regenerate and commit both:

```sh
xcodegen generate
```

Never hand-edit `Zubi.xcodeproj`; the next `xcodegen generate` overwrites it. `Sources/Info.plist` and
`Sources/Zubi.entitlements` are the exception to "generated": both are hand-written, committed, and
referenced from `project.yml`.

Hummingbird is the one SwiftPM package, declared under `packages:` in `project.yml`.
`Zubi.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` pins it and everything it
pulls in, so every build resolves the same source. Zubi itself has no `Package.swift`.

## Build & run

```sh
open Zubi.xcodeproj    # then ⌘R
```

Or from the command line:

```sh
xcodebuild -project Zubi.xcodeproj -scheme Zubi -configuration Debug \
    -derivedDataPath build/DerivedData build
open "build/DerivedData/Build/Products/Debug/Zubi Dev.app"
```

A fixed `-derivedDataPath` keeps the app at one path, so macOS keeps matching it to its grants.
`build/` is git-ignored.

`xcodebuild` uses whatever `xcode-select` points at. If that is the Command Line Tools rather than
Xcode, prefix the command with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.

The release workflow also passes `-skipPackagePluginValidation`. Hummingbird applies no build plugin
today, but a command-line build has nobody to click **Trust & Enable**, so the flag keeps a future
plugin from stopping the release.

## The dev channel

Debug builds are a separate app: **`Zubi Dev.app`**, bundle id `de.fa-krug.zubi.dev`. Everything
persisted is keyed by bundle id:

- `~/Library/Preferences/<id>.plist`: what is exposed, bind address, port, and the update setting.
- `~/Library/Caches/<id>/`: the update check and staged downloads.
- The `SMAppService` login item.
- The TCC grants: Reminders, Calendar and Automation (Notes).

So a local build can neither read nor clobber an installed copy's state, and both run side by side.
Two consequences:

- Don't run both on the same port. Whichever starts second fails to bind.
- The dev build never updates itself. **Check for Updates…** says it is a local build instead.

That includes the API key: its login-keychain item uses the bundle id as its service (account
`api-key`), so each build has its own key and **Regenerate** in one never touches the other.

Anything newly persisted must stay keyed by `Bundle.main.bundleIdentifier`. `AppPaths.caches()` does
that for files.

## Signing in Debug

Debug signs with `Zubi Self-Signed` and runs **without** the hardened runtime. Hardened runtime turns
on library validation, and Xcode's `Zubi Dev.debug.dylib` would be refused at launch, because a
self-signed identity carries no Team ID for the loader to match. Release turns it on. See
[signing.md](signing.md#hardened-runtime).
