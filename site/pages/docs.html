Documentation

Everything about Zubi: the Mac app, the API it serves, and the command-line client that reads it. New here? The three-step setup on the home page is all you need to get going.

How Zubi fits together

Zubi is Basque for “bridge”. The app runs on your Mac, works with Reminders, Calendar and Notes with your permission, and answers HTTP requests for the parts you chose to share: reading them, and adding and editing items where you allowed it. Everything else talks to it.

The Mac app

A menu bar app with no Dock icon. It holds the permissions, decides what is shared, keeps the API key, and runs the server. It must be running, in a logged-in session, for anything to answer.

The API

JSON over HTTP on port 8787, with a bearer key. Described in OpenAPI, browsable on your Mac at /docs and in the API reference.

The command-line client

zubi, one small program for macOS, Linux and Windows. Readable text in a terminal, exact JSON for scripts and agents.

Your devices

A Raspberry Pi, Home Assistant, a laptop, an AI agent, your own code: anything that can reach the Mac and send the key.

Updates

The app checks GitHub once a day, shows the release notes, and installs and relaunches when you say so.

Install

Zubi needs macOS 14 Sonoma or later, on Apple silicon or Intel.

  1. Download the latest Zubi-Universal-<version>.zip from GitHub Releases.
  2. Unzip it and move Zubi to your Applications folder.
  3. Open it. macOS asks once whether to open an app downloaded from the internet; Zubi is signed and notarized by Apple, so confirm. Its bridge icon appears in the menu bar.
  4. To keep it running after a restart, open Settings › General and switch on Launch at login.

The first time Zubi starts, it opens Settings on the Reminders tab, so you can choose what to share straight away. The icon is solid while the server is running and faded while it is stopped. Clicking it shows the address it listens on, the latest requests, and buttons to start or stop the server and to open Settings.

Open Settings from the menu bar icon. Each tab covers one thing:

Choosing what to share

Each list, calendar and folder has its own setting, chosen next to it in Settings:

SettingReadingAdding and editing
Off (the default)Answers 404, as if it didn’t existAnswers 404
ReadYesRefused with 403
Read & WriteYesYes

Moving a reminder or event to another list or calendar needs that one set to Read & Write too. Zubi never deletes anything, whatever the setting. Some calendars can’t be written by anyone, such as subscribed and holiday calendars, so Read & Write isn’t offered for them. Every list, calendar and folder in the API says whether it is writable.

Changes apply to the next request; there is nothing to restart. If you create a list, calendar or folder while Settings is open, click Reload at the bottom of the tab.

Reminders

Under Settings › Reminders, click Grant Access and allow full access in the dialog. Then choose Read or Read & Write for each list. The API returns each reminder’s title, notes, list, priority, due date and whether it is done; you can ask for one list, for what is due today, or for what is overdue. In a writable list it can add reminders, and change their title, notes, due date and priority, complete or reopen them, and move them to another writable list.

Calendars

Under Settings › Calendars, grant access the same way and choose a setting for each calendar. Events come back with title, times, location, notes and URL. A recurring event comes back once per occurrence, and one request covers at most a year. In a writable calendar Zubi can add events and edit them; for a recurring event, an edit changes only the one occurrence you name, never the whole series.

Notes

Apple Notes has no public interface, so Zubi reads it by scripting Notes.app. The first time, macOS asks whether Zubi may control Notes; allow it. Some things follow from that:

  • Notes.app is opened in the background when Zubi needs it.
  • Reading is slower than Reminders or Calendar: a large folder can take a second or two.
  • Locked notes stay locked. Zubi returns their title and dates, never their text, and never changes them.
  • In a writable folder Zubi can add notes, and change a note’s title or replace its text, given as plain text or as HTML.
  • A note’s ID is a long x-coredata:// address. Pass it as the id query parameter, URL-encoded; the command-line client does this for you.

Keys

Every request needs a key, and every device should get its own, under Settings › Keys. Click Add Key…, give it a name you’ll recognise, such as Kitchen Pi, and choose its access:

Read
The device can read what you shared and never change anything, whatever a list, calendar or folder is set to. The right choice for displays, dashboards and calendar subscriptions.
Read & Write
The device can also add and edit, but only in the lists, calendars and folders you set to Read & Write. A change needs both.

Each key’s menu copies its secret (Copy Key) or a ready-made test command, renames it, gives it a new secret, or deletes it; a deleted or regenerated key stops working at once, for that device only. The list shows when each key was last used. A client can ask which key it holds with GET /api/key.

Keys are stored in your Mac’s Keychain. If you used Zubi before keys existed, your old key became the key named Default, with Read & Write access, so nothing stopped working.

Activity

Settings › Activity lists the last 500 things created or edited through the API, newest first: when, which key did it, what changed, and in which list, calendar or folder. It is kept on your Mac only. Clear empties it.

Reaching Zubi from other devices

At first Zubi answers only on your Mac (127.0.0.1), so nothing on your network can reach it by accident. There are four ways to open it up, set under Settings › Server:

Through a relay, from anywhere
Zubi connects out to a relay, and devices on other networks reach it there, with each session encrypted end to end with the device’s key: the relay can’t read anything, and nothing on your Mac accepts connections from the internet. See Through a relay.
Keep it local and tunnel to it (the safest)
Leave Bind to on Localhost only, turn on Remote Login on the Mac, and from the other device run ssh -N -L 8787:localhost:8787 you@mac.local. On that device, Zubi is now at http://127.0.0.1:8787, and the traffic is encrypted by SSH.
A specific address, such as Tailscale
Choose Specific IP and enter the Mac’s address on a private network you trust, for example its Tailscale address. Only devices on that network can reach it, and Tailscale encrypts the traffic.
All interfaces
Zubi answers on every network the Mac is on, and announces itself there, so zubi config discover on another computer finds it without typing an address. Use this only on a network you trust: the API is plain HTTP, so the key and your data travel unencrypted. macOS may ask whether Zubi may accept incoming connections and use the local network.

Click Apply and Restart after changing the address or port. The Mac has to be awake and logged in to answer; with FileVault on, macOS doesn’t log in automatically after a restart. To stop it falling asleep while it serves, switch on Keep this Mac awake while Zubi serves under Settings › General. The display still sleeps as usual.

The API

Every endpoint under /api needs a key from Settings › Keys, sent as a header: Authorization: Bearer <key>. /health, /openapi.json and /docs need none.

RequestReturns
GET /api/listsShared reminder lists, with account and colour
GET /api/keyThe name and access of the key you are using
GET /api/remindersReminders; list, due=today|overdue, completed=true, q to search
GET /api/calendarsShared calendars, with account and colour
GET /api/eventsEvents; from, to (inclusive, default the next 7 days), calendar, q
GET /api/calendars/{id}/events.icsA calendar as a subscription feed (below)
GET /api/notes/foldersShared Notes folders, each with its parent
GET /api/notesNote titles and dates, newest first; folder, limit, q
GET /api/note?id=…One note as plain text and HTML
POST /api/remindersAdd a reminder to a writable list
PATCH /api/reminders/{id}Edit, complete, reopen or move a reminder
POST /api/eventsAdd an event to a writable calendar
PATCH /api/events/{id}Edit an event, or one occurrence of a recurring one (occurrence)
POST /api/notesAdd a note to a writable folder
PATCH /api/note?id=…Change a note’s title or text
GET /api/changesA stream that says when something changed (below)
  • Dates are ISO 8601 in UTC, or YYYY-MM-DD in the Mac’s time zone for all-day items.
  • Fields without a value are left out of a response, never sent as null.
  • Errors answer {"error": {"message": "…"}} with a status that says what went wrong: 400 for a bad parameter or body, 401 for a missing or wrong key, 403 when the Mac hasn’t granted access or the target is shared read-only, 404 for something not shared, 409 for a locked note, 503 when Notes can’t be read or written.
  • In an edit, a field you leave out stays as it is, and null clears it (notes, due date, location, URL).
  • q finds items whose title or notes contain the text, ignoring case. For notes it searches the text too, which can take a few seconds in a large folder.
  • A note’s plaintext and html start with its title; when you write a note, send only the text below the title.

Every parameter and field is in the API reference. On your own Mac, Open API Docs in Settings › Keys opens the same API in Swagger UI, where you can paste a key under Authorize and try each call.

Live changes

GET /api/changes keeps the connection open and sends a short message whenever something changes, so a dashboard can refresh at once instead of asking every minute. Each message says whether reminders, the calendar or notes changed, and whether the change came through Zubi or from somewhere else; it carries no data, so re-read what you show. Reminders and Calendar report every change, made anywhere. Notes can’t report its own changes, so for Notes only changes made through Zubi are announced. From a terminal: zubi watch.

Calendar subscriptions

Calendar apps such as Thunderbird, GNOME Calendar or a wall display can subscribe to a shared calendar by URL. Calendar apps can’t send a key as a header, so the link carries it as ?key=, and for that reason only a Read key works there. Create a Read key for each app, then use its menu’s Copy Calendar Feed URL, or run zubi feed Work. The feed covers the last 30 days and the next year, refreshed whenever the app asks.

Command-line client

zubi reads the same API from a terminal. It is one file with nothing to install alongside it, for macOS, Linux (including a Raspberry Pi) and Windows.

Install

On macOS and Linux, with Homebrew:

brew install fa-krug/tap/zubi

On Windows, with Scoop:

scoop bucket add fa-krug https://github.com/fa-krug/scoop-bucket
scoop install fa-krug/zubi

Both keep it up to date (brew upgrade, scoop update zubi). Otherwise, or for 32-bit Raspberry Pi OS, download the archive for your system from the CLI releases (tagged cli/v…), unpack it, and put zubi on your PATH:

Configure

Tell it where Zubi is and give it a key, once. On the same network as a Mac serving on all interfaces, zubi config discover --save finds the address for you.

zubi config set url http://127.0.0.1:8787
zubi config set key -     # paste the key, then Enter: it stays out of your shell history
zubi health               # checks that Zubi answers

Flags (--url, --key) and environment variables (ZUBI_URL, ZUBI_API_KEY) override the saved settings for a single run. The settings file is readable only by you.

--search (or -q) on reminders, events and notes finds items by their text. In a terminal, lists and calendars show their colours, and the ones shared read-only are marked. --ids on reminders and events prints each item’s ID, ready to paste into an edit command. Set NO_COLOR or pass --no-color for plain text.

Dates and times take YYYY-MM-DD, YYYY-MM-DDTHH:MM in the computer’s own time zone, or full ISO 8601. The commands that change things work only where the list, calendar or folder is set to Read & Write in Zubi.

zubi reminders add "Buy milk" --list Groceries --due 2026-11-02
zubi reminders --list Groceries --ids
zubi reminders done <id>
zubi events add "Dentist" --calendar Personal --start 2026-11-03T09:00 --end 2026-11-03T09:30

For agents and scripts

Pass --json to get the API’s answer exactly as the server sent it, and branch on the exit code. Messages go to standard error, so standard output stays clean JSON.

Exit codeMeans
0Success
1Any other error, including 403 (read-only, or access not granted on the Mac) and 409 (a locked note)
2Bad usage: unknown command or flag, or no key configured
3The key was refused
4Not found, or not shared
5Zubi didn’t answer: not running, wrong address, or no tunnel
 
zubi events --from 2026-11-02 --to 2026-11-06 --json
zubi reminders --due overdue --json | jq -r '.reminders[].title'
zubi reminders add "Call the plumber" --list Errands --due 2026-11-03T09:00 --json

To let an agent such as Claude Code use your calendar, install zubi where the agent runs, configure it once, and tell the agent it may run zubi … --json. Before changing anything, an agent can check the writable field of zubi lists, zubi calendars or zubi folders; writing to something read-only exits with 1 and says how to allow it.

Claude Desktop and MCP

zubi mcp turns the command-line client into a Model Context Protocol server, so assistants without a terminal, such as Claude Desktop, can list and search your reminders, events and notes, and add or edit them where you allow it. Give it its own key. In Claude Desktop’s claude_desktop_config.json:

{
  "mcpServers": {
    "zubi": {
      "command": "/usr/local/bin/zubi",
      "args": ["mcp"],
      "env": { "ZUBI_URL": "http://127.0.0.1:8787", "ZUBI_API_KEY": "<key>" }
    }
  }
}

In Claude Code: claude mcp add zubi -- zubi mcp, after zubi config is set up. The assistant sees which items are writable, and with a Read key it can’t change anything at all.

Through a relay

A relay is where a Mac running Zubi and its clients meet when they are on different networks, such as a MacBook on the road and a Raspberry Pi at home. Both connect out to it and it copies messages between them, so neither has to accept connections. Each session is encrypted end to end between the Mac and the device, with the device’s key: the relay holds no key and sees only which addresses connect, when, and how much they send.

  1. Run a relay, as below, or use one you already have.
  2. On the Mac, under Settings › Server › Relay, turn on Connect through a relay, enter its wss:// address and click Apply.
  3. Under Settings › Keys, choose Copy Pairing Code in the device’s key’s menu. The code holds the key, so keep it as secret.
  4. On the device, run zubi pair - and paste it. zubi checks it with the Mac through the relay, saves it, and from then on every command goes through the relay.

For other programs on that device, zubi tunnel serves Zubi at http://127.0.0.1:8787, each connection through the relay. Requests still need the key, as on the Mac.

Running a relay

zubi relay
Relay ready: wss://203.0.113.7

With no flags it finds the network’s public IPv4 address, gets a six-day certificate for it from Let’s Encrypt, serves wss:// on port 443 and renews the certificate on its own. Let’s Encrypt checks by connecting to port 443 of that address, so it must be reachable from the internet. When it isn’t, the relay says why and exits: it never falls back to unencrypted ws://. --listen :8443 listens elsewhere (forward port 443 to it), --ip or --domain say what to certify, --behind-tls-proxy serves a platform or proxy that provides wss:// itself, and only --no-tls serves plain ws://.

Where to host it, in order of preference:

  1. A machine at home, if you can forward a port, such as the Raspberry Pi itself: free, and nobody else involved. Forward TCP 443 on the router to it and run zubi relay as a service. Your connection needs its own public IPv4 address (not carrier-grade NAT). When your provider changes that address, the relay’s URL changes too; a free DuckDNS name with --domain avoids that.
  2. Render’s free web service, if you can’t forward a port. Render provides wss://, and sees only what any relay sees. A connected Mac’s pings keep the free service from sleeping.
  3. A small server with a public address, such as a VPS or Oracle Cloud’s Always Free tier: run zubi relay as at home, and the address never changes.
  4. Your own reverse proxy or Cloudflare Tunnel, pointed at zubi relay --behind-tls-proxy --listen 127.0.0.1:8080.

The CLI README has a systemd service file, the Render settings and every flag.

Updates

The app checks GitHub for a new release once a day, starting half a minute after launch. When there is one, it shows the release notes; Update Now downloads it, checks that it is signed by the same developer, replaces the app and offers to relaunch. Later skips that version until a newer one comes out. Switch off the daily check under Settings › General; Check for Updates still works. Your settings, permissions and key survive every update.

The command-line client doesn’t update itself: download the new archive, or run go install again.

Security

  • Only what you shared is served, and only what you set to Read & Write can be changed, checked on every request.
  • Every API request needs the key: 32 random bytes generated on your Mac, kept in its Keychain, compared in constant time. Regenerate replaces it immediately.
  • The server listens only on your Mac until you change that.
  • The API itself is plain HTTP. Beyond your Mac, use a relay, whose sessions Zubi encrypts end to end with the device’s key, an SSH tunnel, or an encrypted network such as Tailscale.
  • The API never deletes anything, and never touches a locked note.

Found a vulnerability? Please report it privately, as described in the security policy.

Troubleshooting

“Port 8787 is already in use”
Another app, or a second copy of Zubi, already listens there. Quit it, or choose another port under Settings › Server and click Apply and Restart.
401, or “the API key was refused”
The key is missing or out of date. Copy it again from Settings › Keys; after a key is regenerated or deleted, the devices using it need a new one.
403, “access not granted on the Mac”
Zubi lost or never got permission. If the message says the key is read-only, use a Read & Write key for changes. Open the matching tab in Settings and click Grant Access, or allow Zubi under System Settings › Privacy & Security.
404 for a list, calendar or folder that exists
It is Off in Settings. Shared items are matched by ID or by their exact name.
403, “shared read-only”, when adding or editing
The list, calendar or folder is set to Read. Set it to Read & Write in Settings. When moving an item, the target needs Read & Write too.
Notes answers 503
Zubi may not control Notes. Allow it under System Settings › Privacy & Security › Automation › Zubi › Notes, then click Grant Access under Settings › Notes.
zubi pair says the key was refused
The key was deleted or regenerated after the code was copied. Copy a new pairing code from Settings › Keys.
“The Mac isn’t connected to the relay”
Check Settings › Server › Relay on the Mac: it should say Connected, and the server must be running. The Mac has to be awake.
Another device can’t reach Zubi
Check that the server is running (solid icon), that it listens on an address that device can reach (see Other devices), and that the Mac is awake. zubi health exits with 5 when nothing answers.
